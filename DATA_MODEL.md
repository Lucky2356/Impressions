# Модель данных

БД: SQLite через Drift. Все идентификаторы — UUID v4 (текст). Даты — UTC ISO-8601 или epoch-миллисекунды. Внешние ключи включены (`PRAGMA foreign_keys = ON`).

## 2. Категории — ключевые поля (§17)

`id (UUID)`, `profileId`, `parentId (nullable)`, `name`, `normalizedName`, `description`, `icon`, `color`, `sortOrder`, `level`, `path` (материализованный путь), `defaultTypeId (nullable)`, `coverAttachmentId (nullable)`, `archivedAt (nullable)`, `currentRevisionId`, `createdAt`.

`defaultTypeId` и `coverAttachmentId` ссылаются с `ON DELETE SET NULL`, а не
`RESTRICT`, как остальные связи: категория не должна мешать удалить тип или
фотографию — она теряет украшение, и только.

## 2.1. Стадии и прогресс (§10)

`object_types.statuses_json` — набор стадий типа списком `{key, name, done}`;
`object_types.progress_unit` — в чём считать прогресс. У записи —
`profile_entries.status` (ключ стадии), `progress_current`, `progress_total`.

Ключи стадий общие для всех типов (`planned`, `inProgress`, `done`), названия —
свои у каждого типа. Отбор идёт по ключу, показывается название.

## 2.2. Живые подборки (§27)

`collections.filter_json` — сохранённый отбор каталога (тот же `CatalogState`,
что каталог пишет в настройки). `null` — подборка ручная, её состав лежит в
`collection_entries`; непусто — живая, состав пересчитывается на каждый показ, и
ручного порядка у неё нет.

## 3. Выбор стратегии дерева — обоснование

Рассмотрены:

1. **Adjacency list + recursive CTE** — просто, гибко,但 подсчёт по ветке и хлебные крошки требуют рекурсии на каждый запрос.
2. **Closure table** — быстрые запросы предков/потомков, но дублирование строк (N² на глубокие деревья) и сложное поддержание при перемещении.
3. **Materialized path** — путь хранится строкой; потомки — по префиксу (`path LIKE 'a/b/%'`); быстро и без рекурсии, но перемещение ветки требует обновления префиксов у всех потомков.

**Решение: adjacency list + materialized path.**

- `parentId` — источник истины иерархии (целостность, простое перемещение на 1 уровень).
- `path` (из UUID через `/`) и `level` — денормализованный кэш для быстрых операций:
  - потомки: `WHERE path LIKE :selfPath || '/%'`;
  - предки/хлебные крошки: разбор `path` на сегменты;
  - подсчёт записей в ветке: join `entry_categories` по множеству id ветки (полученному по префиксу);
  - глубина: `level`.
- Перемещение ветки: сменить `parentId`, пересчитать `path`/`level` для узла и всех потомков в одной транзакции; проверить, что новый родитель не входит в поддерево (защита от циклов).
- Для сложных агрегаций дополнительно доступен recursive CTE.

Такой гибрид даёт быстрые чтения (главный сценарий — просмотр и фильтрация) при управляемой стоимости перемещений (редкая операция). Поддержка ≥10 (технически до 20) уровней вложенности.

## 4. Индексы и ограничения

- Уникальность `id` во всех таблицах; уникальность `sha256` вложений.
- Индексы: `categories(profileId, parentId)`, `categories(profileId, path)`, `profile_entries(profileId, objectId)`, `entry_categories(entryId)`, `entry_categories(categoryId)`, `object_revisions(objectId)`, `profile_entry_revisions(entryId)`.
- Частичный уникальный индекс `idx_entry_primary_category ON entry_categories (entry_id) WHERE is_primary = 1` — одна основная категория на запись. Первичный ключ таблицы при этом `(entryId, categoryId)`: любая операция, двигающая связи, уважает оба ограничения сразу.
- FTS5-таблица для полнотекстового поиска по названиям объектов и заметкам.
- Внешние ключи с `ON DELETE RESTRICT` (физическое удаление не является обычной операцией — используется архивирование).

## 5. Версионность (§18)

Каждая revision хранит: `id (UUID)`, `entityId`, `parentRevisionId`, `authorProfileId`, `deviceId`, `createdAt`, `importedAt`, `payloadVersion`, `payloadJson`, `contentHash (SHA-256 полезной нагрузки)`, `originPackageId`. Текущая версия сущности — `currentRevisionId`. `contentHash` обеспечивает идемпотентность импорта (дубли не создаются).

## 6. Миграции

Схема версионируется через Drift `schemaVersion`. Каждая миграция покрыта тестом (см. `TESTING.md`). Перед миграцией создаётся резервная копия (§28).

### Разовые проходы схемы 7

Схема поднимается один раз на весь релиз 1.16.0, поэтому три прохода идут в
одной ступени и оформлены отдельными публичными методами `AppDatabase` —
иначе их нечем было бы проверить тестом:

- `assignDefaultTypesByName()` — ветке проставляется тип по совпадению имён, тем
  же правилом, каким его угадывала форма до 1.16.0. Обязателен `EXISTS`-страж:
  без него подзапрос вернул бы `NULL` там, где типа нет, и затёр уже
  проставленное.
- `seedBuiltInStatuses()` — встроенные типы получают стартовые наборы стадий.
  Только те, у кого их нет: набор могли убрать нарочно, и возвращать его при
  каждом обновлении было бы навязчиво.
- `migrateWantToTryToStatus()` — отношение `wantToTry` становится стадией
  «Задумано», а отношение стирается: «хочу попробовать» — не мнение о вещи, а
  отметка, что мнения ещё нет. Второй оператор чинит перенос между профилями:
  тот писал в колонку стадии ключ отношения. Переход односторонний.

### Повторные впечатления (схема 8)

`entry_visits` хранит каждый отдельный раз: дату, оценку этого раза и заметку.
Сама запись при этом продолжает хранить **последнее**: её `rating` и
`impression_date` обновляются вместе с самым свежим по дате посещением.

Это осознанная денормализация. Каталог, фильтры, сортировки, статистика, итоги
года, экспорт и перенос между профилями читают запись и продолжают работать без
единой правки; считать оценку из посещений на каждый запрос значило бы
переписать всю выборку записей ради того же числа. Обратная сторона —
`profile_entries.rating` теперь означает «оценка последнего раза», а не «оценка
вообще», и это стоит помнить, читая старый код.

Средняя оценка в статистике по-прежнему считается по записям, а не по
посещениям: «мне нравятся фильмы на 8» — про фильмы, а не про число просмотров.

Разовый проход `seedFirstVisits()` заводит первое посещение каждой записи, у
которой есть дата впечатления или оценка. Одним `INSERT ... SELECT`, без чтения
в память. Записи без даты и без оценки пропускаются: посещение «неизвестно когда
и без мнения» — это выдумка за человека.

Удаление записи насовсем уносит её посещения (`purge_service`): ссылка стоит с
`restrict`, и без этого запись просто не удалилась бы.

### Про «ё» в поиске

Токенизатор `unicode61` в SQLite «ё» и «е» не сближает — не помогает и `remove_diacritics 2`. Поэтому свёртка делается сама:

- в триггерах — `replace(replace(x, 'ё', 'е'), 'Ё', 'Е')`, то есть индекс хранит уже свёрнутый текст;
- в запросе — `Normalize.yo`, тем же правилом;
- в нормализованных колонках (`normalized_title`, `normalized_name`) — через `Normalize.name`, чтобы «Ёлка» и «Елка» не разъезжались в два тега или две категории.

Индекс при обновлении набирается запросом, а не командой FTS5 `rebuild`: та читает таблицу-источник напрямую, минуя триггеры, и вернула бы в индекс сырой текст.
