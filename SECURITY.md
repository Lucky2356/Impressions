# Безопасность

Приложение локальное, без сети. Основные угрозы — вредоносные импортируемые файлы и утечка приватных данных при экспорте.

## 1. Модель угроз

| Угроза | Мера |
| --- | --- |
| Вредоносный zip (Zip Slip, обход путей) | Строгая валидация путей при распаковке |
| Подмена/повреждение пакета | SHA-256 + checksums + подпись Ed25519 |
| Подделка авторства профиля | Проверка подписи открытым ключом; фиксация отпечатка |
| DoS через огромные/глубокие файлы | Лимиты размера, количества, глубины JSON/дерева |
| Утечка приватных данных | Явный предпросмотр состава экспорта; локальные заметки не экспортируются |
| Порча БД при сбое импорта | Транзакционность + резервная копия + rollback |
| Геолокация в EXIF фото | Удаление EXIF-геоданных при импорте изображения |

## 2. Криптография

- **Подпись**: Ed25519 (пакет `cryptography`). Закрытый ключ — только локально, вне обычного экспорта, под локальным шифрованием. Открытый ключ и отпечаток — в профиле/экспорте.

### 2.1. Где лежит секрет шифрования закрытого ключа

Закрытый ключ хранится в базе зашифрованным AES-GCM. Ключ этого шифрования (секрет устройства) намеренно вынесен **из базы** — иначе скопированный файл базы содержал бы и замок, и ключ от него.

| Платформа | Где лежит секрет | Что это даёт |
| --- | --- | --- |
| Windows | Отдельный файл, зашифрованный DPAPI (`CryptProtectData`) на учётную запись пользователя | Копия базы вместе с файлом секрета бесполезна на другом компьютере и под другой учётной записью |
| Android | Отдельный файл в приватном каталоге приложения, исключённом из резервных копий | Другие приложения к нему не имеют доступа; секрет не утекает в облачный бэкап |
| Прочее | Таблица настроек в базе (запасной путь) | Прежнее поведение; в настройках честно показывается, что защиты ОС нет |

Секрет, оставшийся в базе от версии 1.0, переносится автоматически при первом обращении к ключу; в базе на его месте остаётся пустая строка.

Готовый плагин (`flutter_secure_storage`) не подошёл: его реализация под Windows требует ATL из состава Visual Studio, которого может не быть на машине сборки. Прямой вызов DPAPI через `dart:ffi` не требует ничего, кроме системной `crypt32.dll`.
- **Хеши**: SHA-256 (`crypto`) для пакета, файлов контейнера, вложений и `contentHash` revisions.
- **Шифрование пакетов**: AES-GCM с ключом из пароля через PBKDF2-HMAC-SHA256 (120 000 итераций, случайная соль на каждый пакет). Пароль не хранится.
- **Паспорт профиля** (перенос своего профиля на другое устройство): зашифрованный контейнер с закрытым ключом.

### 2.2. Резервные копии под паролем

Защита включается в настройках и по умолчанию выключена. Защищённая копия — файл `*.zip.enc`:

```
<строка JSON-заголовка>\n
<шифротекст ChaCha20-Poly1305>
<16 байт кода проверки подлинности>
```

Шифрование и расшифровка идут потоком: копия с фотографиями не поднимается в память целиком. AES-GCM для этого не подошёл — в `cryptography` 2.9 его потоковый вариант накапливает все куски и шифрует их в конце одним куском.

**Ключом шифрования служит не пароль, а случайный ключ копий.** Копии создаются в том числе перед импортом и восстановлением, когда спросить пароль негде. Ключ копий лежит в том же хранилище, что и секрет устройства (см. 2.1), а его копия, зашифрованная паролем, — в заголовке каждого файла копии.

Что из этого следует:

| Случай | Что происходит |
| --- | --- |
| Копия открывается на своём устройстве | Пароль не спрашивается: ключ на месте |
| Копия унесена на другое устройство или открывается после переустановки | Спрашивается пароль, из заголовка достаётся ключ |
| Пароль сменили | Новые копии заворачиваются новым паролем, **уже созданные по-прежнему открываются старым**: заголовок задним числом не меняется |
| Пароль забыт, а устройство утрачено | Копия не восстанавливается — это и есть смысл защиты |
| Настройки говорят «шифровать», а ключа копий нет (например, восстановили копию с чужими настройками) | Копия делается открытой, защита выключается: несделанная копия хуже незашифрованной, но молчать об этом нельзя |

Запасного хранения ключа копий в базе нет намеренно: база целиком попадает в копию, и ключ рядом с зашифрованным им содержимым ничего не защищает.

**Что защита не даёт.** Живая база на диске остаётся незашифрованной — защищается копия, унесённая с устройства, а не само устройство.

## 3. Безопасный импорт (§21)

Перед внесением данных:
1. вычислить SHA-256 пакета; проверить расширение;
2. распаковать во временный каталог;
3. защита от Zip Slip: запрет абсолютных путей, `..`, символических ссылок; каждый нормализованный путь обязан лежать внутри временного каталога;
4. проверить список разрешённых файлов (whitelist структуры контейнера);
5. проверить manifest и версию формата;
6. проверить checksums;
7. проверить подпись;
8. проверить лимиты;
9. полностью разобрать данные;
10. показать предпросмотр;
11. создать резервную копию.

Импорт транзакционен: при любой ошибке БД остаётся в состоянии до импорта (rollback), временные файлы удаляются.

## 4. Лимиты (§21)

- файл ≤ 1 ГБ; одно вложение ≤ 30 МБ; после распаковки ≤ 2 ГБ;
- ≤ 20 000 записей; ≤ 50 000 revisions; ≤ 20 000 вложений;
- глубина категорий ≤ 10 по умолчанию (технический максимум 20);
- ограничение длины строк, глубины JSON, числа пользовательских полей.

Значения — в `AppConfig`.

## 5. Проверка подписи профиля (§22)

- Первый импорт: показать отпечаток, запросить доверие.
- Совпадающий UUID и ключ: «Подпись корректна».
- Совпадающий UUID, другой ключ: импорт останавливается, профили не объединяются автоматически.

## 6. Изображения (§16)

При добавлении: проверка сигнатуры и MIME, отклонение подозрительных файлов, удаление EXIF-геолокации, исправление ориентации, ограничение размера, оптимизированный оригинал + thumbnail, SHA-256 (дедупликация), атомарная запись. Изображения не хранятся в BLOB SQLite; путь к исходному пользовательскому файлу не сохраняется.
