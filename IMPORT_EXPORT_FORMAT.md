# Формат импорта и экспорта

## 1. Файл

Расширение: `.impressions` (хранится в `AppConfig.profileFileExtension`). Файл — подписанный zip-контейнер.

Структура:

```
manifest.json        версия формата, id пакета, профиль, устройство, режим, счётчики
profile.json         передаваемые данные профиля (без локальных настроек)
devices.json         устройства профиля
categories.jsonl     категории (по строке на запись)
objects.jsonl        общие объекты
entries.jsonl        записи профиля (мнения)
revisions.jsonl      неизменяемые revisions
photos.jsonl         связи снимков с версиями записей (с 1.19.0)
visits.jsonl         повторные впечатления записей (с 1.19.0)
attachments/         файлы вложений (имя = sha256)
checksums.json       SHA-256 каждого файла контейнера
signature.json       подпись Ed25519 (открытый ключ + подпись манифеста/контента)
```

## 2. Режимы экспорта (§19)

Весь профиль; только изменения после даты; выбранные записи; выбранная категория; вся ветка категории; подборка; профиль без фото; профиль с фото; публичная версия; защищённая паролем версия; резервная копия собственного профиля.

Каждый профиль экспортируется отдельно. Для чужого профиля учитывается режим повторной передачи: разрешена / нежелательна / запрещена владельцем. При запрете кнопка повторного экспорта чужого профиля не показывается.

Перед экспортом показывается: какой профиль, число записей/категорий/подкатегорий/фото, размер, исключённые приватные данные, дата, устройство, режим.

## 3. Manifest (ключевые поля)

```json
{
  "formatVersion": 1,
  "packageId": "<uuid>",
  "profileId": "<uuid>",
  "profilePublicKey": "<base64>",
  "profileFingerprint": "7A91-1F42-8B03",
  "deviceId": "<uuid>",
  "exportMode": "full | delta | selection | category | branch | collection | backup",
  "createdAt": "<iso8601>",
  "counts": { "entries": 0, "categories": 0, "objects": 0, "revisions": 0, "attachments": 0 },
  "includesPhotos": true,
  "protected": false
}
```

## 3.1. Ссылки между файлами контейнера

Три поля ссылаются на то, что лежит в других файлах пакета, и требуют осторожности при импорте:

| Поле | Где | На что ссылается |
| --- | --- | --- |
| `categories[].defaultTypeId` | `categories.jsonl` | тип из `objects.jsonl` (`kind: "type"`) |
| `categories[].coverSha` | `categories.jsonl` | файл из `attachments/` — **по SHA-256, а не по id** |
| `entries[].categories[].categoryId` | `entries.jsonl` | категория из `categories.jsonl` |
| `photos[].sha256` | `photos.jsonl` | файл из `attachments/` — **по SHA-256** |
| `photos[].revisionId` | `photos.jsonl` | версия записи из `revisions.jsonl` |
| `visits[].entryId` | `visits.jsonl` | запись из `entries.jsonl` |

Обложка ветки едет по хешу, потому что на принимающей стороне у того же снимка будет свой идентификатор: вложения дедуплицируются по SHA-256.

Пакет может ссылаться на то, чего в нём нет: при выгрузке одной ветки или когда фотография отсеялась по приватности. Импорт в таком случае оставляет поле пустым — ветка теряет украшение, но пакет применяется целиком. Поэтому типы применяются **раньше** категорий: ветке нужен уже существующий тип.

Поля `objectTypes.statusesJson`, `objectTypes.progressUnit`, `entries.progressCurrent` и `entries.progressTotal` появились вместе со стадиями (§10) и ни на что не ссылаются. Пакеты, собранные до этого, просто не содержат их — импорт читает отсутствующее поле как пустое.

### Фотографии записей (с 1.19.0)

До 1.19.0 файлы снимков в пакет клали, а связь «этот снимок принадлежит этой
записи» — нет: в чужом профиле фотографии оказывались ничьими, и запись
приезжала без обложки. `photos.jsonl` эту связь и несёт: хеш файла, версия
записи, порядок, пометка обложки и подпись.

Ключом служит **имя файла в пакете** (`attachments/<хеш>.jpg`), а не хеш,
пересчитанный на принимающей стороне: обработка перекодирует снимок, и байты
выходят другие. По той же причине это касается и обложек веток — до 1.19.0 они
совпадали по удаче.

### Совместимость версий

Пакет от 1.18.0 и старше читается: отсутствующие `photos.jsonl` и `visits.jsonl`
разбираются как пустые.

В обратную сторону — нет: список разрешённых файлов контейнера (§21) в 1.18.0
этих имён не знает и отвергнет пакет целиком. Пакет, собранный 1.19.0, нужно
открывать приложением не старше 1.19.0.

`collections.filterJson` — условие живой подборки (§27). Внутри лежит
сохранённый отбор каталога: идентификаторы типа, категории и тегов. Пакет может
приехать в профиль, где этих идентификаторов нет, — тогда подборка просто ничего
не находит. Ронять из-за этого экран нельзя: испорченное или неприменимое
условие читается как «ничего не подходит».

### Отношение «Хочу попробовать» из старых пакетов

Пакет, собранный до 1.16.0, несёт `entries[].relation = "wantToTry"`. Внутри
база такого отношения больше не знает: оно стало стадией. Импорт переводит его
сам — `relation` обнуляется, `status` становится `planned`. Без этого запись
приехала бы с пустым мнением и без стадии, то есть просто потеряла бы пометку.
То же для `status = "wantToTry"`: так помечались записи, перенесённые между
профилями.

## 4. Подпись (§22)

`signature.json` содержит открытый ключ Ed25519, отпечаток и подпись над каноническим представлением `manifest.json` + `checksums.json`. Проверка при импорте гарантирует целостность и авторство. Подробнее — `SECURITY.md`.

## 5. Импорт (§20, §21)

Порядок (см. `SECURITY.md §Импорт`):
1. вычислить SHA-256 пакета; проверить расширение;
2. распаковать во временный каталог с защитой от Zip Slip и лимитами;
3. проверить manifest, версию формата, checksums, подпись;
4. полностью разобрать данные, показать предпросмотр;
5. создать резервную копию;
6. транзакционно применить: новые revisions/объекты/записи/категории/вложения; обновить дерево профиля через revisions;
7. не менять локальные настройки, ничего не удалять физически;
8. показать итог.

Идемпотентность: повторный импорт того же пакета (`packageId`/`contentHash`) не создаёт изменений — «Этот пакет уже был импортирован. Новых изменений нет.»

Результат импорта (пример):

```
Профиль: Александр   Устройство: Samsung S24
Новых записей: 14   Новых категорий: 2   Изменённых записей: 6
Перемещённых категорий: 1   Новых изображений: 9   Без изменений: 103   Конфликтов: 1
```

## 6. Защищённые пакеты

Опционально пакет шифруется (AES-GCM) с ключом, производным от пароля пользователя (KDF). Пароль в файле не хранится. При импорте запрашивается пароль. См. `SECURITY.md`.
